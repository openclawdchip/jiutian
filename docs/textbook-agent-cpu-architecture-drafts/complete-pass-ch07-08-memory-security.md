# 第 7 章 长期任务记忆

## 导读

长期任务不是一次问答的延长版，而是一类状态持续演化的计算过程。一个智能体可能先理解目标，再阅读材料，随后尝试若干方案，记录失败原因，修改计划，等待用户确认，最后在中断、压缩或恢复之后继续执行。如果系统只依赖当前上下文窗口保存这些信息，任务越长，越容易出现遗忘、重复尝试、误解约束和恢复困难。

本章讨论 Agent CPU 如何把“记住任务”转化为体系结构问题。核心思想是：上下文只是下一轮推理的输入视图，不能等同于任务真实状态。真实状态应由 ledger、artifact、trace 和恢复点共同承载；context projection 则是在预算内从这些状态中生成的临时投影。compact 不是把历史随意压短，而是一次受控的状态整理事务。恢复也不是重放全部聊天记录，而是从已提交 ledger、证据引用和恢复锚点重建可继续执行的任务状态。

## 7.1 上下文与记忆的区别

在日常语言中，“上下文”和“记忆”常被混用。但在体系结构设计中，二者承担的职责完全不同。上下文是模型或推理单元当前可见的输入，它强调“此刻要看什么”。记忆是任务跨时间保存的状态，它强调“系统已经承诺什么、知道什么、做过什么、为什么这样做”。

可以把上下文理解为投影，把记忆理解为源数据。投影为了适配窗口大小、注意力预算和当前阶段，会被裁剪、重排、摘要和合并；源数据则要求可追溯、可审计、可恢复。若把投影当成源数据，compact 后的摘要一旦漏掉关键约束，后续推理就会把遗漏当成事实不存在。相反，若把源数据组织成 ledger 和证据引用，即使某一轮投影没有显示某条旧约束，系统仍能在提交前检查它是否被违反。

| 概念 | 主要作用 | 生命周期 | 风险 |
| --- | --- | --- | --- |
| 上下文窗口 | 为当前推理提供输入 | 一轮或数轮推理 | 受预算限制，可能遗漏信息 |
| 长期记忆 | 保存任务真实状态 | 贯穿整个任务 | 若无结构，难以检索与恢复 |
| context projection | 从记忆到上下文的选择结果 | 随阶段重新生成 | 选择错误会误导推理 |
| compact | 对过长历史进行受控整理 | 发生在边界点 | 摘要若无校验会造成失忆 |
| ledger | 已提交状态账本 | 持久存在，可版本化 | 若允许随意覆盖会破坏审计 |

因此，长期任务记忆的第一原则是分离：上下文可以变化，记忆必须稳定；投影可以有取舍，账本必须能说明取舍依据；摘要可以变短，任务承诺不能消失。

## 7.2 Ledger：把任务状态写成账本

ledger 是长期任务记忆的主干。它不是普通日志的同义词。普通日志可能记录大量流水事件，读者需要事后分析才能知道哪些信息仍然有效；ledger 则保存已经提交的任务状态，强调版本、顺序和承诺。一次 ledger 更新通常以 delta 的形式出现：先生成候选增量，再经过检查，最后提交为新版本。

在 Agent CPU 中，可以把 ledger 分成若干类型，各自保存不同语义的状态。

| ledger 类型 | 保存内容 | 典型问题 | 提交要求 |
| --- | --- | --- | --- |
| GoalLedger | 用户目标、成功标准、禁止事项、优先级 | 当前到底要完成什么 | 不能被摘要删除，目标变化需记录原因 |
| PlanLedger | 阶段、待办、依赖、已完成步骤 | 下一步应做什么 | 步骤状态必须与证据一致 |
| EvidenceLedger | 文件、命令、测试、工具输出、观察结果的引用 | 依据从哪里来 | 引用要能回到原始证据或摘要证据 |
| DecisionLedger | 已采用方案、被拒绝方案及理由 | 为什么这样选择 | 关键取舍需要保留反例和条件 |
| RecoveryLedger | 安全点、脏状态、未提交候选、恢复锚点 | 中断后从哪里继续 | 必须区分已提交与未提交副作用 |

这种拆分的好处是让“记忆”变成可检查的数据结构。例如，用户说“不要修改公开接口”，这不是一句容易被压缩掉的自然语言，而应进入 GoalLedger 的禁止事项。某个测试失败，不只是聊天记录中的一段输出，而应进入 EvidenceLedger，并与相关计划步骤、决策理由建立引用。某个方案被证明不可行，应进入 DecisionLedger，避免系统在恢复后重复同一条失败路线。

ledger 的提交也应有顺序。智能体可以并行探索多个候选方案，但只有通过检查的候选 delta 才能进入已提交 ledger。这样，长期任务记忆就像处理器的架构状态：中间推测可以很多，正式可见的状态必须清楚、顺序一致、可回放。

## 7.3 Context Projection：从记忆到当前视图

模型一次推理能看到的内容有限，因此系统必须把长期记忆投影为当前上下文。context projection 的任务不是“尽量塞满窗口”，而是在预算内选择最能支持下一步行动的信息。它通常要回答四个问题：当前目标是什么，当前阶段是什么，哪些证据最关键，哪些限制不能违反。

一个良好的 projection 应包含稳定骨架和阶段内容。稳定骨架包括任务目标、禁止事项、当前计划阶段、最近恢复点和高优先级决策；阶段内容则包括与下一步相关的证据摘要、候选方案、待验证假设和必要的 artifact 预览。稳定骨架不应被短期相关性挤掉，因为它们负责维持任务身份；阶段内容可以随任务推进而变化，因为它们服务于当前局部计算。

| projection 组成 | 来源 | 作用 | 可否裁剪 |
| --- | --- | --- | --- |
| 当前目标与成功标准 | GoalLedger | 约束整个任务方向 | 原则上不可裁剪 |
| 禁止事项与风险边界 | GoalLedger、RecoveryLedger | 防止越界行动 | 不可静默裁剪 |
| 当前阶段与下一步 | PlanLedger | 指导短期行动 | 可压缩但需保留状态 |
| 关键证据 | EvidenceLedger、artifact 摘要 | 支持判断与验证 | 可选取最相关子集 |
| 重要决策理由 | DecisionLedger | 避免重复争论 | 可摘要但需保留结论和条件 |
| 恢复信息 | RecoveryLedger、trace 摘要 | 支持中断后继续 | 至少保留最近安全点 |

projection 必须带有来源标识。它显示的每段事实，都应能追溯到 ledger 项、artifact 摘要或 trace 摘要。这样做有两个意义。第一，模型输出候选动作后，系统可以检查该动作是否基于过期或不完整投影。第二，compact 后即使自然语言摘要发生变化，系统仍能知道摘要对应哪些已提交事实。

教学例子：假设一个智能体正在完成一篇课程报告。GoalLedger 中有“报告应面向本科生”“不得使用未验证数据”；PlanLedger 中显示当前阶段是“整理实验结果”；EvidenceLedger 中有三次实验输出；DecisionLedger 中记录“放弃方案 A，因为样本量不足”；RecoveryLedger 中记录“最近安全点为完成方法章节”。此时 projection 不需要放入全部对话，但必须包含报告对象、禁止事项、当前阶段、三次实验的可信摘要、放弃方案 A 的原因和最近安全点。若窗口不足，应优先压缩实验细节，而不是删除“不得使用未验证数据”。

## 7.4 Compact：受控的状态整理事务

compact 常被误解为“把长对话总结短”。这种理解过于危险。对长期任务而言，compact 是一次状态整理事务：它把过长的临时上下文、工具输出和中间讨论，整理为可持续使用的 ledger delta、artifact 引用、trace 摘要和新的 projection。它既要减少当前可见文本，又不能破坏任务真实状态。

一次合理的 compact 可以分为六步。

| 步骤 | 目标 | 产物 |
| --- | --- | --- |
| 划定边界 | 确定哪些历史进入整理范围 | compact boundary |
| 抽取事实 | 从对话和工具事件中识别目标、证据、决策、风险 | 候选 ledger delta |
| 校验证据 | 检查事实是否有来源，是否与已提交状态冲突 | 验证报告 |
| 提交增量 | 将通过检查的变化写入对应 ledger | 新 ledger 版本 |
| 生成摘要 | 为过长事件生成可追溯摘要 | trace 摘要、artifact 摘要 |
| 打包投影 | 为下一轮推理选择可见内容 | context projection |

compact 的关键不变量是：真实状态先提交，投影后生成。若先写自然语言摘要，再把摘要当成唯一记忆，系统会失去检查能力。正确顺序应当是先从事件中抽取结构化状态，经过验证后提交 ledger，再根据新 ledger 和证据摘要生成 projection。

compact 还要处理失败。若候选 ledger delta 与已有目标冲突，或者某条证据引用不存在，compact 不能把错误摘要写成事实。它应拒绝该 delta，保留失败原因，并回到 compact 前的安全点。这样，compact 失败只是一次整理失败，不会污染长期记忆。

## 7.5 恢复：从提交状态继续任务

长期任务可能因为上下文耗尽、运行中断、权限拒绝、执行失败或用户暂停而需要恢复。恢复的目标不是复原所有历史文字，而是重建足以继续正确行动的任务状态。它应当回答：当前目标是什么，已经完成什么，哪些证据可信，哪些候选尚未提交，下一步应从哪里开始。

恢复通常依赖三个层次。第一层是已提交 ledger，它提供目标、计划、证据、决策和安全点。第二层是 artifact 与 trace 摘要，它们提供必要的原始依据和过程线索。第三层是重新生成的 context projection，它把前两层压入当前可见窗口。

恢复流程可以写成如下顺序：加载最近 ledger 版本；检查 RecoveryLedger 中的安全点和脏状态；确认是否存在未提交候选；丢弃或隔离未提交副作用；按当前目标和计划重新选择证据；生成新的 projection；进入下一步执行。这个流程强调“从提交状态出发”，而不是从最后一段对话出发。

教学例子：一个任务在修改文档时中断。中断前，系统已经提交了“完成章节结构调整”的 PlanLedger 项，也记录了“术语表尚未检查”的待办；某个候选修改还没有通过审核。恢复时，系统应承认已完成的结构调整，保留术语表待办，隔离未提交候选，并重新生成包含目标、当前计划、关键证据和安全点的 projection。它不需要恢复中断前模型的每一句思考，只需要恢复可继续执行的状态。

## 本章小结

长期任务记忆的本质，是把智能体的状态从短暂上下文中解耦出来。上下文用于当前推理，ledger 保存已提交承诺，projection 把长期记忆映射为当前视图，compact 在边界处整理状态，恢复从提交状态重新开始。这样设计后，长任务不再依赖“模型是否还记得”，而依赖系统是否以结构化、可追溯、可审计的方式保存了任务事实。

# 第 8 章 安全与权限

## 导读

智能体执行任务时会读取资料、生成代码、调用工具、修改文件、启动测试，并可能把结果提交为新的任务状态。能力越强，越需要清晰的安全边界。传统程序通常由固定代码和操作系统权限约束；智能体任务则具有动态生成、动态选择工具、动态组织上下文的特点。安全设计不能只问“这个程序能不能运行”，还要问“这个任务被允许看什么、写什么、执行什么、消耗多少资源、留下什么证据”。

本章从能力边界、capability、受控访问、trace 和审计五个方面说明 Agent CPU 的安全与权限模型。其核心目标不是阻止所有行动，而是让行动在可声明、可检查、可追踪、可恢复的范围内发生。一个安全的智能体系统，应当允许低风险任务高效执行，同时让越权访问、预算失控、证据缺失和危险提交在清楚的位置被拦截。

## 8.1 能力边界：安全从任务定义开始

能力边界指一个任务在执行期间能够影响的范围。它包括可读范围、可写范围、可执行工具、可追加 ledger、可访问 artifact、资源预算和用户确认条件。边界越模糊，系统越难判断某个行为是正常执行还是越权。

在长期任务中，最危险的不是单次错误，而是错误被写入持久状态。例如，智能体误读一个文件只是局部问题；若它把误读结果提交到 EvidenceLedger，并在后续 compact 中继续引用，就会形成长期污染。因此，安全边界必须覆盖读、写、提交和摘要，而不仅是文件权限。

| 边界类型 | 控制对象 | 示例问题 | 安全要求 |
| --- | --- | --- | --- |
| 读取边界 | ledger、artifact、输入片段 | 是否允许查看该证据 | 读取需由任务声明并被授权 |
| 写入边界 | 工作区、候选输出、临时缓冲 | 是否允许产生修改 | 默认写入候选区，提交前检查 |
| 执行边界 | 工具、命令、外部动作 | 是否允许调用该能力 | 高风险动作需要额外确认 |
| 提交边界 | ledger delta、正式结果 | 是否允许改变持久状态 | 必须检查证据、版本和权限 |
| 资源边界 | 时间、令牌、内存、调用次数 | 是否可能失控 | 预算耗尽应触发 trap |
| 恢复边界 | 安全点、脏状态 | 失败后能否回退 | 未提交副作用必须可隔离 |

这种边界设计把安全前移到任务准入阶段。任务开始前，系统先检查它请求的能力是否与目标匹配；任务执行中，硬件或运行时继续检查实际访问是否越界；任务结束时，提交逻辑再检查候选结果是否有权成为持久状态。

## 8.2 Capability：可携带、可检查的权限凭证

capability 可以理解为一种明确的权限凭证。与“用户拥有全部权限，程序自己决定怎么用”不同，capability 把权限细分到任务、区域和操作类型。一个任务拿到某个 capability，才可以执行相应访问；没有 capability，即使它知道资源名称，也不能直接使用。

capability 至少应包含四类信息：对象范围、操作类型、有效期和附加约束。对象范围说明它覆盖哪些 ledger 段、artifact 摘要、内存区域或工具；操作类型说明可读、可写、可执行、可追加还是可提交；有效期说明它只对哪个任务、哪个阶段或哪个版本有效；附加约束说明预算、审计级别、是否需要人工确认等条件。

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| subject | 被授权的任务或执行单元 | 某个分析任务、某个验证任务 |
| object | 被访问对象 | 计划账本、证据摘要、候选输出区 |
| operation | 允许操作 | read、append、execute、commit |
| scope | 范围限制 | 只限当前任务、只限某个版本之后 |
| budget | 资源上限 | 最大调用次数、最大字节数、最大时间 |
| trace policy | 记录要求 | 记录摘要、记录完整参数、记录拒绝原因 |

capability 的价值在于减少默认信任。一个生成代码的任务可能只需要读取接口说明、写入候选补丁、运行限定测试；它不应自动拥有修改所有文件、删除证据、提交 ledger 的能力。另一个负责整理证据的任务可以读取工具输出并追加 EvidenceLedger 候选 delta，但不应执行外部命令。通过 capability，系统把“任务需要什么”变成可检查的声明。

教学例子：设有一个“整理实验结果”的任务。它需要读取三份实验输出，追加 EvidenceLedger 候选项，并生成报告摘要。它的 capability 可以允许读取指定 artifact 摘要、向候选证据区追加、读取当前目标；但不允许修改目标、执行新的外部命令、覆盖已提交证据。若任务试图把失败实验删除，检查器应拒绝该写入，因为它超出了追加候选证据的权限。

## 8.3 受控访问：从请求到提交的检查链

安全系统不能只在入口处检查一次。智能体任务具有动态性：它可能在执行中发现新文件、生成新计划、请求新工具，也可能因为 projection 不完整而尝试访问未授权对象。因此，受控访问应贯穿请求、执行、提交三个阶段。

请求阶段关注准入。系统检查任务说明、capability 请求、资源预算和输入来源。如果任务请求的读写范围过大，或者目标与权限不匹配，应在运行前拒绝。执行阶段关注实际访问。每次读、写、工具调用和 DMA 搬运都应带有任务标识与 capability 标识，检查器据此判断是否允许。提交阶段关注持久状态。候选 ledger delta、候选补丁或外部动作结果，只有在证据、版本、权限和审计要求全部满足后，才可以成为正式结果。

| 阶段 | 检查内容 | 失败结果 |
| --- | --- | --- |
| 准入 | 请求的 capability 是否合理，预算是否完整 | 拒绝任务或要求缩小范围 |
| 执行 | 实际访问是否匹配 capability | trap，并记录原因 |
| 候选生成 | 输出是否在候选区，是否带证据 | 保留候选但禁止提交 |
| 提交 | delta 是否有权改变 ledger，版本是否一致 | 拒绝提交，写入拒绝记录 |
| 恢复 | 是否存在未提交副作用 | 隔离、回滚或请求确认 |

受控访问还要求读写分离和候选区隔离。智能体可以生成候选修改，但候选修改不应自动成为正式状态。它可以提出 ledger delta，但 delta 必须经过验证。这样即使执行单元出现错误，也不会直接污染已提交记忆。

## 8.4 Trace：让行为留下可解释轨迹

trace 是安全模型的时间维度。capability 回答“是否允许”，trace 回答“实际发生了什么”。没有 trace，系统也许能拒绝一部分越权行为，却难以解释为什么拒绝、拒绝发生在哪个任务、哪些状态已经改变、恢复应从哪里开始。

一个有用的 trace 不必保存所有原始数据，但必须保存足以审计和恢复的关键字段：任务标识、时间顺序、访问对象、capability 标识、操作类型、结果、资源消耗、证据引用和失败原因。对高风险操作，trace 还应记录更完整的参数摘要和确认信息。对低风险重复操作，trace 可以分层压缩，但不能丢失边界事件。

| trace 事件 | 记录重点 | 用途 |
| --- | --- | --- |
| capability check | 请求权限、实际对象、允许或拒绝 | 定位越权来源 |
| memory access | 读写区域、字节范围、版本 | 解释数据来源 |
| tool call | 工具、参数摘要、返回摘要 | 审计外部影响 |
| ledger delta | 基线版本、候选变化、证据引用 | 检查提交正确性 |
| trap | 任务、原因、当前位置、已用预算 | 支持恢复和教学 |
| compact | 边界、摘要来源、提交版本 | 防止摘要失真 |

trace 与 ledger 的关系也需要区分。ledger 保存已提交状态，trace 保存状态变化过程。ledger 告诉我们“现在任务承诺了什么”，trace 告诉我们“这些承诺如何产生”。审计通常需要二者配合：若某条 EvidenceLedger 项可疑，trace 应能显示它来自哪次工具调用、经过哪次 compact、由哪个 capability 授权提交。

## 8.5 审计：把安全变成可验证制度

审计是对系统行为的事后与在线检查。它不是附加文档，而是安全体系的一部分。审计要检查权限是否最小化、访问是否合规、拒绝是否准确、提交是否有证据、compact 是否保留关键约束、恢复是否从正确安全点开始。

审计可以分为三类。第一类是在线审计，在任务运行时检查高风险动作，例如越权写入、预算耗尽、缺少证据的提交。第二类是提交审计，在候选结果进入 ledger 或正式输出前检查版本、证据和权限。第三类是离线审计，在任务完成后回放 trace 和 ledger，评估系统是否存在过度授权、重复失败路径或摘要失真。

| 审计问题 | 需要查看的材料 | 合格标准 |
| --- | --- | --- |
| 是否过度授权 | capability 请求与实际 trace | 未使用的高风险权限应被移除 |
| 是否越权 | capability check 事件 | 越权访问被准确 trap |
| 是否证据充分 | EvidenceLedger 与 tool trace | 关键结论均可追溯 |
| 是否安全提交 | ledger delta 与基线版本 | 无未授权覆盖和版本冲突 |
| compact 是否可靠 | compact 边界与摘要来源 | 目标、禁止事项、失败结论未丢失 |
| 恢复是否正确 | RecoveryLedger 与 trap trace | 未提交副作用被隔离 |

教学例子：某任务被授权读取资料摘要并生成候选计划，但 trace 显示它尝试直接提交 DecisionLedger。审计器应指出两个问题：执行阶段发生 capability violation；任务设计可能混淆了“生成候选计划”和“提交决策”的职责。修正方式不是给它更大权限，而是把提交决策交给具有审计要求的后续任务。

## 8.6 安全与长期记忆的结合

第 7 章讨论了长期任务记忆，本章讨论了安全权限。二者在 Agent CPU 中必须合在一起。没有安全的记忆会被错误状态污染；没有记忆的安全又难以解释和恢复。capability 约束谁能读写 ledger，trace 记录访问过程，审计检查 compact 和提交是否可靠，RecoveryLedger 则在 trap 后提供继续执行的入口。

特别要注意 projection 的安全性。projection 是模型可见内容，若它删掉禁止事项或伪造证据，后续推理会在错误前提上行动。因此，projection 生成也应受 capability 和审计约束：它只能读取被授权的 ledger 和 artifact；它必须保留高优先级目标与禁止事项；它应标明来源；它不能把未提交候选伪装成已提交事实。

安全模型的最终目标不是让系统寸步难行，而是让每一步都有边界、有依据、有记录。这样，智能体可以大胆探索候选方案，却只能谨慎提交正式状态；可以高效压缩历史，却不能删除承诺；可以在失败后恢复，却不能把失败伪装成成功。

## 本章小结

Agent CPU 的安全与权限设计，应从任务能力边界出发，用 capability 表达可检查权限，用受控访问贯穿准入、执行和提交，用 trace 记录行为过程，用审计验证系统是否遵守边界。安全不是单个开关，而是一条从任务声明到长期记忆提交的检查链。只有当权限、证据、预算、trace 和恢复机制共同工作时，智能体任务才能在强能力与可控性之间取得平衡。
