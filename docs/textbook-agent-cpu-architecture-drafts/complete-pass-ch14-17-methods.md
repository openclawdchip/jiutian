# 方法与实验篇：第 14-17 章草稿

# 第 14 章 Benchmark 方法

## 本章导读

体系结构研究不能只停留在概念命名和结构图展示上。一个新体系是否成立，最终要回答三个问题：它面向什么工作负载，它比什么基线更好，它用什么证据证明这种改进不是偶然现象。Benchmark 方法正是把这些问题转化为可测、可复现、可比较实验的学术语言。

对于 Agent CPU 而言，Benchmark 的意义更加突出。传统处理器常以指令吞吐、缓存缺失、分支预测、能耗和面积作为基本评价对象；智能体系统则包含模型推理、工具调用、状态维护、证据追踪、权限检查、失败恢复和人工确认等环节。若只测一次模型推理延迟，无法解释一个长任务为什么成功、为什么失败，也无法说明硬件和系统软件的贡献在哪里。本章讨论如何为 Agentic workload 建立 Benchmark 方法，使学生能够从可观察现象出发，逐步形成严格的实验评价。

## 14.1 Benchmark 的基本作用

Benchmark 不是简单的“跑分”。在体系结构课程中，它至少有四个作用。第一，它定义研究对象。没有工作负载，处理器设计只能停留在抽象效率上；有了工作负载，研究者才知道要优化的是整数计算、浮点计算、数据库事务、图计算、机器学习推理，还是多步智能体任务。第二，它提供共同语言。不同研究团队可以在相同输入、相同指标和相同规则下比较方案，避免只展示最有利于自己的个别例子。第三，它暴露瓶颈。一个端到端任务慢，可能是计算慢、存储慢、调度慢，也可能是恢复状态不可靠。Benchmark 应帮助研究者把总体表现拆解为可解释的阶段。第四，它约束研究伦理。若实验不能复现、指标选择随意、失败样例被隐藏，那么体系结构结论就缺乏可信度。

经典 Benchmark 的经验值得继承。SPEC 强调稳定程序集合、标准输入和可比较报告；MLPerf 强调端到端任务、精度约束和提交规则。这些思想告诉我们，Benchmark 不只是选择几个样例，而是定义一整套实验契约：输入是什么，输出如何判定，哪些优化允许，哪些统计量必须报告，失败情况如何记录。

## 14.2 Agentic Benchmark 的对象

Agentic workload 的核心不是一次函数调用，而是围绕目标展开的多步行动序列。一个智能体任务通常经历目标理解、计划形成、上下文选择、工具执行、观察反馈、结果验证和提交输出等阶段。每个阶段都可能消耗资源，也可能引入错误。因此，Agentic Benchmark 的对象应包括“过程”，而不仅是“最终答案”。

可以把一个任务表示为事件流。事件流中包含用户目标、系统计划、模型生成、工具调用、工具返回、状态写入、权限检查、错误处理和最终提交。Benchmark 不要求所有系统内部实现相同，但要求它们面对相同的任务条件，并输出足够的轨迹信息以供评价。这样，研究者才能比较不同架构对状态、控制和恢复的支持能力。

在 Agent CPU 语境下，还需要区分两个层次。第一是智能体任务层，关注用户目标是否完成、证据是否充分、约束是否保留。第二是体系结构机制层，关注任务表示、状态存储、上下文投影、工具事件调度、权限隔离和恢复锚点选择等机制是否有效。好的 Benchmark 应能在两个层次之间建立联系：当端到端质量变化时，研究者可以追溯是哪类机制导致变化。

## 14.3 工作负载设计

设计工作负载时，首先要覆盖典型任务，而不是只选择最容易成功的任务。面向 Agent CPU 的工作负载可以分为四类。

第一类是信息综合任务。系统需要读取多份资料，抽取事实，形成带引用的结论。例如比较几种算法、整理一组实验记录、解释一个技术标准。它考察上下文选择、证据保留和文本生成质量。

第二类是工具执行任务。系统需要调用计算、检索、编译、测试或数据处理工具，并根据结果调整计划。它考察工具调用调度、错误处理、状态更新和结果验证。

第三类是长程维护任务。系统在多轮交互中持续修改计划，可能经历上下文压缩、中断恢复和用户要求变化。它考察记忆组织、任务恢复、约束保留和重复劳动控制。

第四类是安全边界任务。系统面对权限限制、敏感数据、不可逆副作用或需要人工确认的操作。它考察能力检查、行动隔离、候选提交和可解释拒绝。

这些任务不一定都要很大。微基准可以隔离某个机制，例如上下文打包在固定预算下能保留多少关键约束，权限检查能否准确发现越界行动，恢复算法能否选择合适的继续点。宏基准则应模拟完整任务，让多个机制共同工作。课程实验中可以先用微基准建立直觉，再用宏基准观察机制组合后的复杂行为。

## 14.4 指标体系

Agentic Benchmark 的指标应避免单一化。速度很重要，但速度不能替代正确性、安全性和可恢复性。一个系统若输出更快，却丢失用户约束、引用不存在的证据，或把未经确认的副作用提交出去，就不能称为更好的系统。

正确性指标关注任务是否完成。常见指标包括最终答案匹配、事实一致性、证据覆盖率、约束保留率和工具结果使用正确率。对于开放式文本任务，不能只做字符串比较，应结合人工评分、规则检查和证据追踪。

性能指标关注资源和时间。可以报告端到端延迟、分阶段延迟、吞吐量、尾延迟、模型调用次数、工具调用次数、上下文搬运量和存储访问量。分阶段延迟尤其重要，因为 Agent CPU 的贡献可能主要出现在模型之外，例如状态整理、权限判断、恢复定位和上下文选择。

安全指标关注系统是否遵守边界。可以测越权行动召回率、误报率、危险提交率和拒绝解释质量。恢复指标关注中断、失败或上下文压缩后能否继续任务，包括恢复成功率、重复错误率、恢复所需信息量和恢复后质量下降幅度。

最后还应报告成本指标，包括计算成本、能耗估计、存储占用和人工确认次数。智能体系统常常通过增加推理轮数来提高质量，Benchmark 应揭示这种质量提升是否值得。

## 14.5 基线与消融实验

没有基线，就没有比较。Agent CPU 的 Benchmark 至少应设置三类基线。第一类是朴素软件基线，即不引入专门体系结构机制，只用通用程序组织智能体循环。第二类是增强软件基线，即通过缓存、索引、规则检查或调度策略改进软件系统。第三类是目标架构方案，即引入专门的任务状态、上下文、权限或恢复支持。只有当目标方案超过合理软件基线，才能说明新机制有研究价值。

消融实验用于回答“到底是哪一部分起作用”。例如去掉证据索引后，证据覆盖率是否下降；关闭恢复锚点后，中断恢复是否更容易重复旧路径；禁用权限预检查后，危险行动是否更多进入执行阶段。消融实验不只是附加材料，而是体系结构论文和教材实验中训练因果推理的核心方法。

基线和消融都要注意公平性。不同方案应使用相同任务输入、相同资源预算和相同评价规则。若某个方案获得更多模型调用次数或更大上下文窗口，就需要明确说明，并把它作为资源差异纳入解释。

## 14.6 可复现报告

一份合格的 Benchmark 报告应包含任务描述、数据来源、输入规模、基线设置、硬件与软件环境、评价指标、统计方法、失败样例和结论边界。对于 Agentic workload，还应补充任务轨迹摘要、工具调用分布、状态恢复场景、权限模型和人工评分协议。

统计报告不能只给平均值。长任务中一次极慢的恢复、一次错误提交或一次证据丢失，可能比平均延迟更重要。因此应同时报告中位数、尾延迟、方差和失败率。对于人工评分，应说明评分标准、评分者数量和一致性检查方法。

可复现并不意味着所有系统必须公开全部内部实现，但至少应让他人能够复查实验结论的关键依据。教材中的实验报告可以采用较小规模，但必须保留完整方法：任务如何生成，指标如何计算，结论如何从数据推出。

## 14.7 小结

本章讨论了 Agentic Benchmark 的方法。Benchmark 是体系结构研究的共同语言，它把工作负载、基线、指标和报告规则连接起来。Agent CPU 面向多步智能体任务，因此评价对象应包括过程轨迹、状态变化、权限边界和恢复能力。好的 Benchmark 既要测性能，也要测正确性、安全性、恢复性和成本；既要有端到端宏基准，也要有机制级微基准；既要展示成功，也要解释失败。

## 习题

1. 为什么只测量单次模型推理延迟不足以评价 Agentic workload？
2. 设计一个信息综合任务的 Benchmark，说明输入、输出和正确性指标。
3. 什么是消融实验？以恢复机制为例说明它如何帮助判断因果关系。
4. 在安全边界任务中，应报告哪些指标才能避免“只看成功率”的偏差？
5. 选择一个熟悉的智能体应用，画出它的事件流，并标出可能的性能瓶颈。

# 第 15 章 教学实验

## 本章导读

教材中的实验不是项目手册的复刻。项目手册告诉学生如何配置环境、运行命令和提交文件；教学实验则要帮助学生形成概念、掌握方法、理解取舍，并能把实验现象转化为体系结构问题。本章把 Agent CPU 的教学实验组织为一组递进任务：从观察智能体循环开始，到测量状态开销、设计上下文策略、分析权限边界，最后完成一个小型研究报告。

教学实验的目标不是训练学生记住某个仓库结构，也不是让学生机械复现教师给出的结果，而是让学生通过实验理解：智能体系统为什么不同于传统程序，体系结构如何支撑它，实验数据如何支撑论证。

## 15.1 教学实验的学习目标

本篇实验可以设置四类学习目标。

第一类是概念目标。学生应能解释 Agentic workload、任务状态、上下文投影、工具调用、证据链、权限边界和恢复锚点等术语，并能用例子说明它们在一次任务中的作用。

第二类是测量目标。学生应能采集任务轨迹，区分端到端延迟和分阶段延迟，统计模型调用、工具调用、上下文长度、状态读写和失败重试，并能用图表解释瓶颈。

第三类是设计目标。学生应能提出一种改进策略，例如更好的上下文选择、更清晰的状态摘要、更早的权限检查或更稳健的恢复方法，并通过对照实验评价它。

第四类是表达目标。学生应能写出结构清楚的实验报告，包括问题、方法、数据、分析、局限和改进方向。体系结构学习不只在代码中发生，也在论证中发生。

## 15.2 实验一：观察智能体循环

第一个实验应尽量简单。教师提供一个固定任务，例如“根据三段资料回答一个问题，并给出证据”。学生不需要修改系统，只观察任务如何进行：系统如何理解目标，如何选择资料，如何生成中间结论，如何检查答案，最终如何提交。

学生应记录每一轮循环的四个要素：当前状态、下一步行动、观察结果和状态更新。通过这张表，学生会看到智能体执行不是线性脚本，而是带反馈的过程。若某一步资料不足，系统可能回到检索；若工具返回错误，系统可能改用另一种方法；若答案缺少证据，系统可能重新定位来源。

本实验的关键不在复杂性，而在形成观察语言。教师可要求学生回答：哪一步是模型推理，哪一步是工具执行，哪一步是状态维护，哪一步体现了停止条件。这样，后续实验才有共同基础。

## 15.3 实验二：测量上下文与状态

第二个实验关注上下文预算。智能体系统无法把全部历史都放入当前上下文，因此必须选择、压缩或索引信息。学生可以在固定任务下比较三种策略：保留最近历史、保留显式摘要、保留与目标最相关的证据片段。

实验指标包括最终答案正确率、关键约束保留率、证据覆盖率、上下文长度和运行时间。学生应分析：最近历史策略是否容易遗忘早期约束；摘要策略是否可能丢失细节；相关片段策略是否依赖检索质量。这里的核心问题是状态表示的取舍：信息越多不一定越好，信息越少也可能导致错误，体系结构需要在容量、带宽、延迟和可靠性之间平衡。

教师可以引导学生把上下文看作一种受限资源，类似缓存容量。缓存课程中要讨论命中率和替换策略；Agent CPU 中则要讨论约束命中、证据命中和任务恢复所需状态。这个类比能帮助学生把新问题放回体系结构传统。

## 15.4 实验三：工具调用与分阶段延迟

第三个实验关注性能拆解。学生选择一个需要工具调用的任务，例如计算表格指标、运行测试、检索文档或生成图表。要求记录端到端时间，并进一步拆分为目标理解、上下文准备、模型等待、工具执行、结果解析、验证和提交等阶段。

学生通常会发现，端到端延迟并不等于模型延迟。工具排队、文件读取、格式转换、错误重试、权限确认和结果检查都可能成为瓶颈。若一个系统把所有慢都归因于模型，就会错过体系结构和系统软件可优化的空间。

本实验还可以加入尾延迟分析。多数工具调用很快，但少数失败重试会显著拖慢任务。学生应学会报告分布，而不是只报告平均值。对于交互式智能体，尾延迟会直接影响用户体验；对于批量智能体，尾延迟会影响资源利用和调度公平性。

## 15.5 实验四：权限边界与候选提交

第四个实验关注安全和副作用。教师可以设计一个任务，其中某些行动只允许生成候选结果，不能直接提交；某些数据可以读取但不能外传；某些操作需要人工确认。学生需要观察系统如何判断权限，如何解释拒绝，如何把候选行动与真实副作用分离。

这个实验帮助学生理解，Agent CPU 的“执行”不只是算得快，还包括知道什么不能执行。传统处理器有特权级、页表和异常机制；智能体系统也需要能力边界、操作审计和可恢复的候选状态。若系统把不确定操作直接变成不可逆副作用，即使最终答案看起来正确，也存在严重风险。

评价指标可以包括越权行动发现率、误报率、候选提交正确率和拒绝解释质量。教师应强调，安全实验不能只统计成功完成任务的次数，还要关注系统如何处理危险路径。

## 15.6 实验五：中断恢复

第五个实验模拟长任务中的中断。学生让系统完成一半任务后停止，删除或压缩部分上下文，再要求系统继续。不同恢复策略会产生不同结果：有的重复已经完成的工作，有的忘记用户约束，有的错误延续旧假设，有的能够从最小必要状态恢复。

学生应记录恢复前的任务状态、保留下来的信息、恢复后的第一步行动、最终质量和重复劳动量。通过比较，学生会理解恢复不是简单的“重新打开历史记录”，而是选择一个合适的继续点。这个继续点既要包含目标、计划和证据，也要避免带入已经被否定的路径。

本实验与操作系统中的检查点、数据库中的日志恢复和处理器中的异常恢复有相似之处。教学中可以鼓励学生进行跨领域类比，但也要指出智能体恢复的特殊性：恢复对象包括自然语言目标、工具观察、推理假设和用户偏好，而不只是寄存器和内存。

## 15.7 实验报告与评分

实验评分不应只看结果是否跑通。建议采用四个维度。第一，概念是否清楚，学生是否正确使用术语。第二，方法是否严谨，是否有基线、指标和对照。第三，分析是否可信，是否能从数据推出有限结论，而不是过度宣传。第四，反思是否具体，是否能指出实验局限和下一步改进。

教师可要求每组学生提交一页图表摘要和一份完整报告。图表摘要训练学生提炼主要发现，完整报告训练学生展开方法和证据。课堂讨论中，教师可以选择失败案例进行讲解，因为失败往往最能暴露体系结构问题。

## 15.8 小结

本章把 Agent CPU 的教学实验组织为从观察到设计的递进过程。实验的重点不是复现某个工程流程，而是帮助学生理解智能体循环、状态表示、上下文预算、工具延迟、权限边界和中断恢复。通过这些实验，学生应学会把现象转化为指标，把指标转化为论证，把论证转化为新的研究问题。

## 习题

1. 为“观察智能体循环”实验设计一张记录表，至少包含四个字段。
2. 为什么上下文预算可以类比为缓存容量？这个类比有哪些局限？
3. 在工具调用实验中，端到端延迟应拆分为哪些阶段？
4. 设计一个需要候选提交的安全实验，并说明如何评价它。
5. 中断恢复实验中，如何判断系统是在真正恢复，而不是简单重做？

# 第 16 章 从教材到研究计划

## 本章导读

教材学习的终点不应只是掌握已有概念，还应能够提出新的研究问题。Agent CPU 仍处在形成期，许多术语、边界和评价方法尚未完全稳定。这既带来困难，也带来机会。学生若能把课程中的概念、实验和现象组织成研究计划，就能从“学习者”逐步进入“研究者”的位置。

本章讨论如何从教材内容出发形成研究计划。研究计划不是宏大的口号，而是一组可回答的问题：现有系统有什么不足，拟议机制解决什么问题，用什么基线比较，用什么指标评价，预期贡献和风险是什么。

## 16.1 从现象到问题

研究问题通常来自反复出现的现象。例如，智能体在长任务中容易忘记早期约束；工具调用失败后容易重复同一错误；上下文压缩后证据链断裂；权限检查太晚导致危险行动已经接近执行；多智能体并发时资源占用不公平。这些现象本身还不是研究问题，需要进一步抽象。

把现象转化为问题，可以经过三个步骤。第一，描述现象发生的条件。是在任务很长时，还是工具很多时，还是上下文预算很小时？第二，说明现象造成的后果。是降低正确性、增加延迟、提高成本，还是引入安全风险？第三，提出可验证的因果假设。例如“若在任务轨迹中显式保存被拒绝路径，则恢复后重复错误率会降低”。这样的假设可以被实验检验。

一个好的研究问题应具有适度范围。问题太小，只是工程调参；问题太大，无法在课程或论文周期内验证。适合学生项目的问题往往聚焦一个机制，例如上下文选择、证据索引、恢复锚点、权限预检查、任务调度或候选提交。

## 16.2 文献与概念定位

研究计划需要说明自己站在什么传统上。Agent CPU 不是凭空出现的概念，它与计算机体系结构、操作系统、数据库、编译器、机器学习系统、人机交互和安全等领域都有联系。学生不必一次覆盖所有文献，但应能找到最相关的三类背景。

第一类是体系结构背景，例如定量评价、存储层次、乱序执行、异常恢复、虚拟内存和加速器设计。它们提供了机制设计和性能分析的语言。第二类是智能体系统背景，例如工具调用、规划、记忆、检索增强生成和多轮交互。它们说明工作负载为什么不同。第三类是可靠性与安全背景，例如审计、权限、隔离、可验证输出和故障恢复。它们帮助研究者避免只看速度。

概念定位的目标不是堆砌引用，而是说明研究空白。比如，传统缓存替换研究处理程序地址流，但智能体上下文选择处理的是语义约束和证据片段；传统检查点保存机器状态，但智能体恢复还要保存目标、假设和被否定路径。通过这样的比较，研究计划才能显示新问题的必要性。

## 16.3 提出机制假设

研究计划的核心是机制假设。机制假设应说明拟议方法如何改变系统行为。例如：“将任务状态分为目标、证据、计划和风险四类，并分别设置保留策略，可以在相同上下文预算下提高约束保留率。”这个假设包含对象、方法、条件和指标，比“改进智能体记忆”更可研究。

机制假设要避免过度承诺。学生常说“提出一种高效可靠的智能体架构”，但这太宽泛。更好的写法是“在固定模型和固定任务集上，比较基于最近历史、人工摘要和结构化状态三种策略对恢复成功率的影响”。这样的研究即使结果没有显著提升，也能产生清楚结论。

机制设计还要说明代价。结构化状态可能提高恢复质量，却增加记录开销；权限预检查可能减少危险行动，却增加误报；并行探索可能提高成功率，却增加计算成本。体系结构研究的价值正在于解释这些取舍，而不是只宣称单方面变好。

## 16.4 实验计划

实验计划应围绕假设展开，而不是把能跑的任务都跑一遍。一个基本实验计划包括工作负载、基线、变量、指标和分析方法。

工作负载要覆盖假设相关场景。如果研究恢复，就必须包含中断、压缩或失败；如果研究权限，就必须包含允许、拒绝和需要确认的行动；如果研究上下文选择，就必须包含早期约束和后期证据之间的冲突。基线要足够强，至少包括朴素方法和一种合理改进方法。变量要明确，例如上下文预算大小、任务长度、工具失败率或并发智能体数量。

指标应同时覆盖收益和代价。研究上下文选择时，既要看正确率和证据覆盖率，也要看上下文构造时间和存储占用。研究权限检查时，既要看危险行动拦截率，也要看误报对任务完成的影响。研究调度时，既要看吞吐，也要看尾延迟和公平性。

分析方法应预先写清。学生应说明如何处理失败运行，如何计算平均值和置信区间，如何展示分布，如何解释异常样例。预先设定分析方法能减少“看到结果后再选择指标”的偏差。

## 16.5 研究计划的结构

一份课程级研究计划可以采用以下结构。

第一部分是问题陈述，用一段文字说明研究现象、后果和核心问题。第二部分是背景与相关工作，说明已有方法为什么不足。第三部分是机制设计，描述拟议方法的基本思想和系统位置。第四部分是实验方法，列出工作负载、基线、指标和变量。第五部分是预期结果与风险，说明可能成功的证据，也说明可能失败的原因。第六部分是时间安排，把工作拆成可完成的阶段。

这里的时间安排很重要。研究计划应保留探索空间，但不能没有里程碑。一个八周项目可以安排为：前两周复现实验和收集基线，第三至四周实现机制原型，第五至六周跑主要实验，第七周补充消融和失败分析，第八周撰写报告。若机制实现失败，仍应能交付基线测量和问题分析。

## 16.6 从课程项目到论文问题

课程项目和论文研究的区别，不在于前者简单、后者复杂，而在于论证要求不同。课程项目可以证明学生理解方法；论文问题需要证明相对于已有工作有新贡献。要从课程项目走向论文问题，通常需要三个扩展。

第一是扩大外部有效性。不能只在一个人工任务上有效，而要覆盖一类任务。第二是增强比较基线。需要与已有系统或公开方法比较，而不只是与自己写的朴素版本比较。第三是深化机制解释。不能只报告结果更好，还要说明为什么更好、在哪些条件下更好、在哪些条件下无效。

有些负面结果也有研究价值。例如，结构化状态在短任务中不如最近历史策略，因为记录开销超过收益；权限预检查在模糊任务中误报较高，需要与人工确认结合。只要方法严谨，负面结果同样能帮助学科理解边界。

## 16.7 小结

本章说明了如何从教材学习走向研究计划。研究从现象开始，但必须经过问题抽象、文献定位、机制假设和实验设计，才能形成可验证计划。Agent CPU 的研究问题往往围绕状态、上下文、工具、权限、恢复和调度展开。好的研究计划范围适中、指标明确、基线公平，并能解释收益与代价。

## 习题

1. 选择一个智能体失败现象，把它改写为一个可检验的研究假设。

3. 为“上下文选择策略”设计一个包含三种基线的实验计划。
4. 课程项目要发展为论文问题，通常需要补强哪些方面？
5. 写出一个八周研究计划的里程碑安排，每周目标不超过两句话。

# 第 17 章 学科建设纲领

## 本章导读

当一种新计算形态出现时，学科建设比单个系统更重要。若没有共同术语，研究者难以交流；若没有课程体系，学生难以进入；若没有 Benchmark 和开放数据，结论难以比较；若没有伦理与安全规范，技术发展可能偏离公共利益。Agent CPU 的学科建设，需要把体系结构、智能体系统、操作系统、安全、人机交互和教育组织在同一个问题空间中。

本章不是提出行政口号，而是从教材角度讨论一门新兴方向如何被教学、研究和社区共同塑造。它回答四个问题：学科对象是什么，课程如何组织，研究共同体需要哪些基础设施，长期发展应坚持哪些原则。

## 17.1 学科对象与边界

Agent CPU 的学科对象，是支撑智能体工作负载的体系结构与系统机制。它关注的不只是某个大模型，也不只是某个应用界面，而是多步目标执行所需的计算基础：任务表示、状态管理、上下文搬运、工具调度、权限隔离、证据追踪、恢复机制和资源分配。

这个边界有两点需要澄清。第一，Agent CPU 不替代传统 CPU、GPU 或 NPU。它研究的是在智能体工作负载中，通用控制、神经网络计算、存储系统和外部工具如何协同，以及哪些新机制值得体系结构层面支持。第二，Agent CPU 不等同于“把智能体写成软件框架”。软件框架很重要，但学科问题还包括可测工作负载、抽象接口、状态语义、资源模型和安全边界。

学科边界应保持开放。早期不宜把定义锁死，因为工作负载和系统形态仍在变化。但边界也不能无限扩张，否则任何 AI 应用都可被称为 Agent CPU。一个实用判断是：若问题涉及多步智能体执行的状态、控制、资源或安全，并且需要体系结构或系统机制解释，就属于本方向的核心区域。

## 17.2 课程体系

一门完整课程可以分为四个模块。第一模块是基础概念，介绍传统体系结构、工作负载、定量评价和智能体循环。学生应理解为什么新工作负载会推动新架构问题。第二模块是核心机制，讨论任务状态、上下文、工具调用、权限边界、恢复和调度。第三模块是实验方法，训练 Benchmark 设计、指标选择、基线比较和报告写作。第四模块是研究前沿，围绕开放问题组织论文阅读和项目展示。

课程不应把所有时间用于讲模型能力。模型是重要组成部分，但本课程重点在“模型之外的系统组织”。教师应不断追问：状态在哪里，证据如何保存，错误如何恢复，权限如何约束，资源如何分配，指标如何证明。这样的追问能把学生从应用演示带回体系结构思维。

实验课应与理论课交替进行。讲完 Agentic workload 后安排观察实验；讲完上下文和状态后安排预算实验；讲完工具和调度后安排分阶段延迟实验；讲完安全后安排权限边界实验；讲完恢复后安排中断恢复实验。课程最后以小型研究计划或项目报告收束，让学生经历从概念到证据的完整过程。

## 17.3 教材组织原则

教材写作应坚持三个原则。第一，从熟悉概念进入新问题。可以从程序、进程、缓存、异常、虚拟内存和 Benchmark 等经典概念出发，再引入智能体任务中的对应变化。这样学生不会觉得新术语悬浮在空中。

第二，保持机制和实验并重。只讲机制会变成概念清单，只讲实验会变成操作手册。教材应在每个关键机制后给出可观察现象和可测指标，让学生知道这个机制为什么需要、如何评价、有什么局限。

第三，承认不确定性。新兴方向中，许多答案尚未固定。教材可以明确标注“已较稳定的基础概念”和“仍在研究中的问题”。这不是削弱教材权威，而是训练学生理解科学知识如何形成。真正的教材不是把所有问题伪装成已有结论，而是教学生如何在证据中前进。

## 17.4 研究共同体基础设施

学科建设需要公共基础设施。首先是开放 Benchmark。它应包含任务集、输入数据、评价脚本、报告模板和失败案例。Benchmark 不必一开始很大，但必须有清晰版本和可复现规则。

其次是术语表和概念图。Agent CPU 涉及多个领域，同一词语在不同领域含义可能不同。共同体需要维护核心术语的解释，例如任务状态、上下文投影、候选提交、恢复锚点、证据覆盖率和能力边界。术语表不是为了统一思想，而是为了减少误解。

第三是教学资源。包括讲义、实验说明、评分样例、可视化工具和小规模数据集。优秀的教学资源能降低进入门槛，让不同学校的学生都能参与。

第四是复现实验库。研究论文应尽可能提供任务配置、基线结果和失败样例。复现实验不只是验证他人结论，也能帮助新研究者发现未解决问题。

## 17.5 伦理、安全与责任

智能体系统能调用工具、处理数据并产生副作用，因此学科建设必须把伦理和安全放在基础位置。学生需要理解，系统能力越强，越需要边界、审计和责任分配。一个能自动修改文件、发送请求或执行实验的智能体，必须说明何时需要人工确认，如何记录行动，如何处理敏感信息，如何撤销或补救错误。

伦理教育不应只在课程最后出现。Benchmark 设计时要考虑隐私和偏差；实验任务中要避免诱导危险行为；研究计划中要说明风险控制；项目报告中要记录失败和限制。这样，安全不是附加章节，而是贯穿方法的基本维度。

还要避免把智能体系统拟人化到失去责任边界。系统可以表现出规划和对话能力，但责任仍由设计者、部署者和使用者共同承担。体系结构研究应提供可审计、可解释、可约束的机制，使责任能够被追踪。

## 17.6 产业与教育协同

Agent CPU 的发展离不开产业实践。真实智能体任务来自软件开发、科学计算、教育辅导、数据分析、办公自动化和设备控制等场景。产业可以提供问题、数据和约束，教育可以提供概念、方法和人才。二者协同时，要避免把课程变成某个产品培训，也要避免研究脱离真实需求。

较好的方式是围绕开放问题合作。例如，如何评价长任务恢复，如何减少工具调用浪费，如何在本地设备上保护隐私，如何为边缘智能体分配资源，如何让审计记录既完整又不过度暴露敏感内容。这些问题既有实际价值，也有学术深度。

学生项目可以连接真实场景，但应经过抽象。教师需要帮助学生从具体应用中抽出体系结构问题，而不是停留在“做一个应用”。例如，从“做一个代码助手”抽象出工具调用调度和候选提交；从“做一个文档助手”抽象出证据覆盖和上下文压缩；从“做一个实验助手”抽象出数据 provenance 和恢复机制。

## 17.7 长期研究议程

长期看，Agent CPU 方向至少有六类核心问题。第一，任务表示：如何把自然语言目标、计划、证据和行动表示为可调度对象。第二，状态层次：如何在上下文窗口、短期记忆、长期存储和外部工件之间分配信息。第三，执行机制：如何协调模型推理、工具执行和传统计算资源。第四，安全隔离：如何让系统在能力增强的同时保持边界清晰。第五，恢复与审计：如何在中断、失败和争议中重建过程。第六，评价体系：如何用 Benchmark 连接质量、性能、成本和责任。

这些问题不会由单篇论文解决，而需要课程、实验、开源工具、产业案例和标准化努力共同推进。学科建设的目标不是尽快制造一个封闭答案，而是形成一个可持续提问、验证和修正的共同体。

## 17.8 小结

本章提出了 Agent CPU 学科建设的基本纲领。它的对象是支撑智能体工作负载的体系结构与系统机制，课程应围绕概念、机制、实验和研究组织，教材应连接经典体系结构与新兴智能体问题。共同体需要 Benchmark、术语表、教学资源和复现实验库，也需要把伦理、安全和责任贯穿始终。只有当教学、研究和实践形成良性循环，Agent CPU 才能从概念走向成熟学科方向。
