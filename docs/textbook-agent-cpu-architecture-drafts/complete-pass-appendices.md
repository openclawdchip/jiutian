# 附录 A-F

本附录面向课堂教学与自学使用。它不依赖某个特定代码仓库，也不要求读者已经参与过工程项目。六个部分分别提供术语表、教学大纲、概念对应表、课程实验手册、APU-IR 示例库和 Benchmark Rubric。教师可以按课程进度选用，学生也可以把它作为复习、练习和课程设计的参考材料。

使用时可遵循一个简单顺序：先用术语表统一词汇，再用教学大纲把各章内容排入学习节奏；随后通过概念对应表把已有体系结构知识迁移到 Agent CPU；接着完成课程实验，把抽象概念落实到任务图、权限表、证据表和恢复锚点；最后阅读 APU-IR 示例并尝试按 Rubric 评价一个小型智能体任务。这样安排的重点不是记住某种固定格式，而是学会用体系结构方法分析智能体系统：识别工作负载，明确接口，约束能力，记录过程，评价结果。对自学者而言，最有效的方式是每读完一个章节，就回到附录中选一个练习改写自己的例子。对授课者而言，本附录可作为课堂讨论、作业说明和课程设计评分的共同语言。

## 附录 A 术语表

**Agentic workload**：以目标为牵引、以多轮智能体循环为基本形态的工作负载。它通常包含目标理解、上下文维护、工具调用、观察反馈、计划调整和结果提交。与一次函数调用或一次模型推理不同，它关注完整任务如何在若干步中推进。

**任务型 Agent**：面向“完成一件事”的智能执行体。它不是只回答单个问题，而是在给定目标和约束下，持续维护状态、选择工具、解释观察并更新计划。课程中可把它看成运行在语义层上的执行单元。

**Agent CPU**：用于讨论智能体工作负载的体系结构抽象。它并不等同于某一颗实际芯片，而是把处理器、运行时、调度器、记忆系统、工具接口和安全机制放在同一框架下，研究如何支撑多步智能任务。

**Agent Domain**：与传统计算域相对的任务语义域。传统计算域更关注指令、寄存器、缓存和算术单元；Agent Domain 更关注目标、计划、上下文、证据、权限和任务状态。二者不是替代关系，而是上下协作关系。

**APU-IR**：面向 Agent Processing Unit 的中间表示。它把自然语言目标、任务图、权限、预算、证据和 trace 转化为可调度、可检查、可审计的结构化对象。教学中可把它理解为 Agent 与执行平台之间的任务级契约。

**任务图**：由节点和依赖边组成的任务结构。节点表示检索、推理、计算、验证、写作等可执行单元；边表示先后关系、数据依赖或控制依赖。任务图的价值在于让隐含的行动序列变成可分析的结构。

**权限**：任务节点能够访问或调用的资源范围。权限可以包括读取材料、调用工具、写入产物、访问数据库或发起外部请求。良好的权限设计强调最小必要能力，使每个节点只获得完成自身任务所需的资源。

**预算**：对任务消耗的限制或指导。预算可以是时间、费用、模型调用次数、工具调用次数、内存、能耗或人工确认次数。预算让开放任务具有工程边界，也帮助调度器在多个可行路径之间做选择。

**证据**：支撑输出结论的来源与依据。证据可能来自输入文档、检索片段、工具返回值、实验数据或验证节点。证据不保证结论天然正确，但提供了复核路径，使生成结果能够被检查和讨论。

**trace**：任务执行过程的记录，包括节点状态、开始和结束时间、输入输出摘要、预算消耗、权限使用、失败和重试信息。trace 面向过程可观察性，常用于调试、复盘、评测和审计。

**上下文**：Agent 在当前任务中可用且正在使用的信息集合。它包括用户目标、已知事实、约束条件、历史步骤、工具观察、中间草稿和待办事项。上下文不是资料堆积，而是服务当前行动的工作空间。

**长期记忆**：跨任务或跨会话保留的信息。它可能保存用户偏好、领域知识、历史决策、常用工具结果或已完成产物。长期记忆需要与当前上下文区分，否则容易造成无关信息干扰或过期信息污染。

**context projection**：把较大的历史状态投影成当前任务所需的紧凑上下文。它通常需要保留目标、硬约束、未完成事项、关键证据和最近决策，同时压缩或移除低价值细节。

**ledger**：对任务状态变化的结构化记录。它关注“什么被确认、什么被修改、什么被提交、什么被拒绝”。在课程中，ledger 可作为理解长任务恢复和责任边界的辅助概念。

**candidate commit**：候选提交。Agent 在写入最终结果或执行有副作用操作前，先生成可检查的候选变化。候选提交允许系统或人类审阅风险、证据和影响范围，再决定是否正式提交。

**回滚**：当某条执行路径失败、越权、证据不足或预算超限时，系统退回到较早的安全状态。回滚不只是撤销文本，还可能涉及上下文、任务图节点、工具观察、候选产物和权限状态。

**恢复锚点**：中断、压缩或失败后用于继续任务的最小充分状态。好的恢复锚点应保留目标、关键约束、当前进度、未决问题和不能重复的失败尝试，避免恢复后从头摸索。

**capability trap**：当任务节点试图使用超出授权范围的能力时触发的拦截。它不仅要拒绝操作，还应说明涉及哪个节点、哪个资源、什么原因和可能的替代路径。

**Agentic Benchmark**：面向智能体工作负载的评测方法。它不仅测速度，还测证据覆盖、约束保留、权限违规捕获、恢复成功率和错误副作用率。它继承 SPEC 与 MLPerf 的定量精神，但测量对象更偏向任务状态流。

**约束保留率**：评测 Agent 是否在长任务中持续保留用户硬约束的指标。例如预算上限、禁止访问外部网络、必须引用来源、不得修改主文档等，都可以成为约束保留的检查对象。

**证据覆盖率**：关键结论中有多少能够回指到明确来源。它常用于评价生成报告、技术分析、实验总结等任务的可复核性。覆盖率高不等于推理完美，但覆盖率低通常说明结果不可靠。

**恢复成功率**：系统在 compact、中断、工具失败或上下文丢失后，能否回到正确任务阶段并继续推进的比例。对长任务 Agent 而言，它与单次推理延迟同样重要。

**bad commit rate**：错误副作用被正式提交的比例。典型错误包括写入未经验证的结论、覆盖重要文件、重复执行已拒绝方案、越权访问资源或把候选结果误当成最终结果。

## 附录 B 教学大纲

本课程可安排为 8 到 12 周模块，也可作为计算机体系结构、智能系统或系统软件课程中的专题单元。推荐先讲传统体系结构接口，再引入 Agentic workload，最后讨论 APU-IR、执行模型、记忆系统和 benchmark。

**模块一：工作负载如何推动体系结构。** 学习目标是理解为什么体系结构研究总是从工作负载开始。课堂可回顾数值计算、事务处理、互联网服务和深度学习对 CPU、GPU、NPU 的影响，再讨论智能体系统为什么形成新负载。练习题可要求学生选取一个日常智能体任务，标出其中的推理、工具、状态和反馈。

**模块二：Agentic workload 的基本结构。** 学习目标是掌握目标、上下文、行动选择和反馈更新四要素。教师可用“生成实验报告”“规划课程活动”“调试程序错误”等例子展示多轮循环。课堂讨论重点是：为什么只测一次模型调用不足以评价整个任务。

**模块三：从 ISA 到 APU-IR。** 学习目标是建立接口层次观念。学生应能比较 ISA、ABI、编译器 IR 和 APU-IR 的作用边界，说明任务级契约为什么需要表达权限、预算、证据和 trace。课后练习可让学生把自然语言任务改写成简化的 APU-IR。

**模块四：任务图与调度。** 学习目标是把线性对话转化为可调度结构。课堂可使用有向图表示检索、筛选、综合、验证、写作之间的依赖关系。重点讨论哪些节点可并行、哪些节点必须等待证据、哪些节点在预算不足时可降级。

**模块五：权限与安全边界。** 学习目标是理解 Agent 的能力越强，越需要细粒度约束。课堂可比较“整个 Agent 拥有全部权限”和“每个节点拥有最小权限”的差异。练习可要求学生为同一任务设计两套权限方案，并分析风险。

**模块六：预算与成本模型。** 学习目标是把开放任务纳入可管理范围。学生应能区分硬预算和软预算，理解时间、费用、模型调用、工具调用和人工确认的取舍。可引入简单的代价公式，让学生估计不同任务图的总延迟。

**模块七：证据、trace 与可复核性。** 学习目标是理解自然语言结果如何进入工程化检查。课堂可展示一段没有来源的总结和一段带证据绑定的总结，让学生比较可信度。练习可要求为三条结论标注证据，并说明哪些结论仍需验证。

**模块八：长任务记忆与恢复。** 学习目标是理解 compact、中断和失败后如何继续任务。教师可给出一段被截断的任务历史，让学生构造恢复锚点。讨论问题包括：哪些信息必须保留，哪些信息可以压缩，哪些失败路径不应重复。

**模块九：候选提交与副作用控制。** 学习目标是理解“生成候选结果”和“正式改变系统状态”之间的边界。课堂可比较写草稿、修改文件、发送邮件和执行数据库更新的风险差异。练习可要求学生设计候选提交审查表。

**模块十：Agentic Benchmark。** 学习目标是掌握评测负载、baseline、指标和报告格式。学生应能解释为什么速度、正确性、安全性、恢复性要一起看。课程设计可要求学生提出一个小型 benchmark，并给出输入、输出、评分规则和失败样例。

若课程时间较短，可合并模块五与九，合并模块七与八。若课程时间较长，可增加实践讨论，如工具沙箱、检索系统、上下文压缩、任务图可视化和人机协同审阅。期末项目不宜只要求“做一个聊天机器人”，而应要求提交任务图、权限表、预算表、证据样例、trace 摘要和评测报告。

## 附录 C 概念对应表

本表帮助读者把熟悉的计算机体系结构概念迁移到 Agent CPU 语境。对应关系是一种教学类比，不表示二者在实现上完全相同。

| 传统体系结构概念 | Agent CPU 中的对应概念 | 教学说明 |
|---|---|---|
| 指令 | 任务节点 | 指令是低层可执行动作，任务节点是语义层可执行动作，如检索、验证或生成。 |
| 程序计数器 | 当前任务阶段 | 程序计数器指向下一条指令，任务阶段指示当前应推进的目标、节点或待办。 |
| 寄存器 | 短期上下文槽 | 寄存器保存近期计算值，短期上下文保存当前推理最需要的事实、约束和中间结果。 |
| 内存 | 任务记忆与资料库 | 内存保存数据，任务记忆保存长期事实、历史决策、外部资料和产物摘要。 |
| Cache | 上下文缓存 | Cache 缓解访存延迟，上下文缓存减少重复检索和重复解释。 |
| 分支预测 | 行动路径预测 | 分支预测猜测控制流，行动路径预测估计哪条任务分解或工具调用更可能有效。 |
| 乱序执行 | 独立节点并行 | 乱序执行利用指令级并行，任务图调度利用检索、验证、分析等节点间的并行。 |
| 提交阶段 | 候选提交确认 | 处理器按序提交保证状态一致，Agent 在确认候选结果后才写入最终产物或产生副作用。 |
| 异常 | 权限 trap 与工具失败 | 异常打断普通指令流，权限 trap 或工具失败打断任务流程并要求恢复策略。 |
| 回滚 | 恢复到安全任务状态 | 传统回滚撤销推测执行，Agent 回滚撤销无效计划、错误候选和不可信证据链。 |
| ISA | 任务级接口契约 | ISA 规定机器指令行为，APU-IR 规定任务节点、权限、预算、证据和 trace。 |
| 性能计数器 | trace 事件与任务指标 | 性能计数器记录硬件事件，trace 记录任务执行事件、预算消耗和失败重试。 |
| Benchmark suite | Agentic Benchmark | 传统套件比较程序性能，Agentic Benchmark 比较任务完成质量、安全性和恢复能力。 |

使用该表时，要避免两种误解。第一，不要把类比当作一一对应的实现蓝图。Agent 的“上下文槽”并不一定有固定字长，也不一定由硬件寄存器实现。第二，不要忽略语义层的独特性。任务节点的正确性常依赖证据、权限和自然语言约束，不能只用算术输出判等。

课堂上可以让学生扩展本表。例如，要求学生寻找“虚拟内存”“TLB”“中断控制器”“流水线冒险”“内存一致性”在 Agent CPU 中可能对应的概念，并说明类比在哪些地方成立、在哪些地方失效。这个练习的目标不是制造术语，而是训练跨层抽象能力。

## 附录 D 课程实验手册

本实验手册提供五个可在课堂或自学中完成的小实验。它们不依赖特定工程环境，教师可以用纸笔、电子表格、脚本语言或课堂讨论完成。每个实验都强调学习目标、输入材料、操作步骤和提交物。

**实验一：识别 Agentic workload。** 目标是区分普通程序、一次性模型推理和多步智能体任务。教师给出三个场景：计算一组数的平均值，回答一道百科问题，整理若干资料并写出带引用的分析。学生需要为每个场景标出输入、输出、状态、反馈和停止条件。提交物是一张对比表和一段简短说明。

**实验二：把自然语言任务改写成任务图。** 目标是学习任务分解。输入任务为“根据四份课程材料，为下周讨论课准备一页提纲，并列出仍需教师确认的问题”。学生先列出候选节点，如读取材料、抽取主题、合并重复观点、生成提纲、检查引用、列出未决问题；再画出依赖关系。提交物包括任务图和每个节点的一句话说明。

**实验三：设计权限与预算。** 目标是理解最小权限和成本控制。沿用实验二的任务图，学生为每个节点分配权限，例如只读课程材料、调用摘要工具、写入最终提纲、不得访问外部网络。随后设定预算，如总时间 10 分钟、模型调用 5 次、检索 0 次、人工确认 1 次。提交物是一张权限预算表，并说明哪两个节点最容易越权或超支。

**实验四：证据绑定与 trace 摘要。** 目标是训练可复核输出。教师提供三段材料和一份示例总结，其中故意混入一条证据不足的结论。学生需要为每条主要结论绑定材料来源，标记证据不足项，并写出简化 trace：读取了哪些材料、抽取了哪些结论、哪一步发现问题、如何修正。提交物包括证据表和 trace 摘要。

**实验五：中断恢复与候选提交。** 目标是理解长任务状态管理。教师给出一段任务历史：用户要求生成报告，系统已完成资料抽取和部分草稿，但在验证阶段中断；同时有一个候选修改尚未确认。学生需要构造恢复锚点，列出恢复后第一步行动，并判断候选修改能否提交。提交物包括恢复锚点、行动计划和提交判断。

评分建议采用“结构清晰、约束完整、证据可查、风险可解释”四个维度。实验不要求学生实现复杂系统，重点在于能否把智能体任务转化为结构化对象。对编程基础较强的班级，可增加一个可选扩展：用 JSON 或 YAML 表达任务图，再写一个小脚本检查权限字段和预算字段是否齐全。

## 附录 E APU-IR 示例库

本示例库使用简化文本格式展示 APU-IR 思想。字段名称不是标准语法，重点是表达目标、任务图、权限、预算、证据和 trace。教师可让学生阅读、修改或扩展示例。

**示例一：课程材料摘要。**

```text
task: course_note_summary
goal: 根据三份课程材料生成一页中文摘要，并列出三个讨论问题
graph:
  read_materials -> extract_topics -> merge_topics -> write_summary -> verify_evidence
permissions:
  read_materials: read(given_materials)
  write_summary: write(draft_answer)
budget:
  time: 8min
  model_calls: 4
evidence:
  write_summary: 每个主要观点至少绑定一份材料
trace:
  record: 节点状态、证据缺口、预算消耗
```

教学提示：这个例子适合展示证据要求。学生可以讨论，如果 `verify_evidence` 发现某个观点没有来源，任务图应回到 `extract_topics` 还是 `write_summary`。

**示例二：实验结果分析。**

```text
task: analyze_lab_results
goal: 比较三组实验数据，说明哪组结果最稳定
graph:
  load_tables -> compute_metrics -> compare_groups -> write_conclusion -> sanity_check
permissions:
  load_tables: read(input_tables)
  compute_metrics: call(calculator)
  write_conclusion: write(report_section)
budget:
  time: 12min
  tool_calls: 3
evidence:
  write_conclusion: 结论必须引用均值、方差或异常值说明
trace:
  record: 读取表格、计算公式、异常数据处理方式
```

教学提示：这个例子适合讨论工具观察。计算工具给出指标后，Agent 还需要解释指标与“稳定性”的关系。

**示例三：校园活动方案。**

```text
task: plan_school_energy_week
goal: 生成适合初一年级的节能周活动方案，预算不超过 3000 元
graph:
  clarify_constraints -> collect_examples -> draft_schedule -> estimate_budget -> revise_plan -> final_check
permissions:
  collect_examples: read(reference_examples)
  estimate_budget: call(spreadsheet)
  revise_plan: write(candidate_plan)
budget:
  time: 20min
  model_calls: 6
  money_limit: 3000
evidence:
  final_check: 明确说明日程、预算和学生参与环节
trace:
  record: 预算变更、被删除活动、最终假设条件
```

教学提示：这个例子适合展示预算不仅是计算资源，也可以是任务内容中的业务约束。

**示例四：带权限限制的资料检索。**

```text
task: restricted_research_brief
goal: 使用给定资料写一段技术背景，不访问外部网络
graph:
  read_sources -> extract_claims -> draft_brief -> check_policy
permissions:
  read_sources: read(provided_sources)
  extract_claims: no_network
  draft_brief: write(draft_answer)
budget:
  time: 6min
  model_calls: 3
evidence:
  draft_brief: 所有事实性陈述必须来自 provided_sources
trace:
  record: 权限检查、来源片段、被拒绝的外部访问请求
```

教学提示：这个例子适合讨论 capability trap。如果某节点试图检索互联网，系统应记录违规原因并要求改用给定资料。

**示例五：中断后的恢复。**

```text
task: resume_report_revision
goal: 继续修改一份报告草稿，保持原有结构并补全证据
graph:
  load_recovery_anchor -> inspect_open_items -> verify_existing_claims -> patch_missing_evidence -> submit_candidate
permissions:
  load_recovery_anchor: read(task_state)
  patch_missing_evidence: write(candidate_revision)
  submit_candidate: require_review
budget:
  time: 15min
  model_calls: 5
evidence:
  submit_candidate: 列出新增证据和未修改部分
trace:
  record: 恢复锚点、未决事项、候选提交差异
```

教学提示：这个例子适合讨论恢复锚点。恢复不是简单重读全部历史，而是保留足以继续任务的最小状态。

## 附录 F Benchmark Rubric

Agentic Benchmark 的评分不应只看“更快完成”。一个系统可能在延迟上更短，却遗漏用户硬约束；也可能生成流畅文本，却无法说明证据来源；还可能在中断后重复已经失败的方案。因此，本 Rubric 建议从正确性、安全性、恢复性、效率和报告质量五个维度评价。

**一、正确性。** 关注最终产物是否满足任务目标。高分答案应覆盖用户要求的主要内容，保留硬约束，区分事实、推断和假设，并能指出未决问题。可采用 0 到 4 分：0 分表示目标基本未完成；1 分表示只完成表面文本；2 分表示完成主要内容但遗漏重要约束；3 分表示内容基本正确且约束较完整；4 分表示结果准确、结构清晰、假设和边界说明充分。

**二、证据质量。** 关注结论是否可复核。评分可检查关键结论的来源绑定、引用是否对应原文、工具计算是否可重现、证据不足处是否被标记。高分系统不应把无来源猜测伪装成事实，也不应把工具返回值机械拼接为结论。

**三、安全性。** 关注权限边界和副作用控制。评分点包括：越权请求是否被拦截，trap 是否说明节点、资源和原因，候选提交是否经过确认，是否避免写入未经验证的结果。安全性不只面向隐私，也面向教学中的严谨性：学生应理解“能做”与“被允许做”是两回事。

**四、恢复性。** 关注系统在中断、失败或上下文压缩后能否继续任务。高分系统应保留目标、关键约束、已完成事项、未决问题和失败路径；恢复后不应从头重复，也不应丢失用户禁止事项。可用恢复成功率、恢复锚点最小性和重复错误率进行量化。

**五、效率。** 关注时间、调用次数和状态处理成本。效率评价应分阶段报告，例如任务接收、工具事件扫描、上下文整理、模型等待、验证和提交。对于 Agentic workload，平均延迟和尾延迟都重要，因为一次极慢恢复可能破坏整体体验。

**六、报告质量。** 关注 benchmark 是否可复现。一个完整报告应包含任务描述、输入规模、事件分布、baseline、权限模型、预算设置、评分规则、失败样例和主要结论。只给最终分数而不给失败样例，难以支持教学讨论。

建议总分为 100 分：正确性 25 分，证据质量 20 分，安全性 20 分，恢复性 15 分，效率 10 分，报告质量 10 分。若课程重点是体系结构性能，可适当提高效率比重；若课程重点是可信智能体，可提高证据与安全比重。无论权重如何，Rubric 都应坚持一个原则：没有证据、约束和恢复能力的速度提升，不能单独证明 Agent CPU 设计更好。

课堂使用时，教师可以给出两个系统的同一任务 trace，让学生按 Rubric 打分并解释差异。期末项目则可要求学生提交一份小型 benchmark 报告，说明他们选择的工作负载、baseline、指标、失败案例和改进建议。这样，benchmark 不只是分数表，而成为理解智能体体系结构取舍的学习工具。
