# 配置与生成流程

九天 v0.1 采用“规格先行、模拟器验证、RTL 固化”的配置流程。配置系统的目标不是隐藏复杂度，而是让每一次模拟、benchmark 和未来 RTL 生成都有可追踪输入。

## 1. 配置目标

配置系统需要回答：

- 当前运行实例有多大？
- 每个 memory space 的容量是多少？
- task 的资源预算是多少？
- trace 输出到什么粒度？
- DMA 使用同步模型还是延迟模型？
- 后续 RTL 参数如何从同一配置派生？

v0.1 先使用 APU-IR 顶层 `config` 字段作为配置入口。

## 2. 当前配置入口

示例：

```json
{
  "config": {
    "host_bytes": 64,
    "cluster_bytes": 1024,
    "spm_bytes": 1024
  }
}
```

字段说明：

| 字段 | 含义 | 默认值 |
|---|---|---:|
| `host_bytes` | host memory 容量 | 4096 |
| `cluster_bytes` | Cluster SRAM 容量 | 4096 |
| `spm_bytes` | 每 core SPM 容量 | 65536 |

这些参数由模拟器读取，并用于创建 memory model。

## 3. Task 级配置

Task 级配置放在 `budget` 字段中：

```json
{
  "budget": {
    "cycles": 64,
    "spm_bytes": 1024,
    "cluster_bytes": 1024
  }
}
```

当前强制执行：

- `cycles`

当前记录但尚未完全强制：

- `spm_bytes`
- `cluster_bytes`
- 后续 `dma_ops`
- 后续 `trace_bytes`

## 4. 配置分层

后续配置应分为四层：

### 4.1 Architecture Config

描述硬件形态：

- cluster 数量。
- 每 cluster core 数量。
- 每 core thread 数量。
- SPM 容量。
- Cluster SRAM 容量。
- DMA channel 数量。
- barrier 数量。

### 4.2 Runtime Config

描述运行时策略：

- task queue 深度。
- 调度策略。
- timeout 策略。
- SPM 清理策略。
- trap 处理策略。

### 4.3 Simulator Config

描述模拟器行为：

- trace 格式。
- 是否输出 summary。
- DMA 延迟模型。
- NoC 延迟模型。
- 是否强制对齐检查。

### 4.4 Benchmark Config

描述评估场景：

- 输入规模。
- 数据分布。
- 重复次数。
- baseline。
- 输出报告路径。

## 5. 生成物

配置流程后续可生成：

- 模拟器配置快照。
- benchmark 运行配置。
- RTL 参数头文件。
- trace schema 文件。
- 文档化配置报告。
- 实现覆盖矩阵草案。

## 6. 可覆盖与不可覆盖文件

配置工具可以覆盖：

- `build/` 下的运行结果。
- `reports/` 下的报告。
- 后续 `generated/` 下的参数文件。

配置工具不得覆盖：

- `README.md`
- `docs/whitepaper.md`
- `docs/glossary.md`
- `specs/*.md`
- 手写测试用例

任何自动生成文件都必须标注生成来源。

## 7. 推荐生成文件头

```text
Generated by: jiutian-config
Source: <input config>
Do not edit manually.
```

## 8. 版本锁定

配置文件应包含版本：

```json
{
  "schema": "jiutian.config.v0.1"
}
```

工具读取未知 major 版本时应拒绝运行；读取未知 minor 版本时可以警告后继续。

## 9. 当前命令路径

当前 v0.1 尚未提供独立配置工具。最小路径是直接运行包含 `config` 字段的 APU-IR：

```powershell
python simulator\jiutian_sim.py simulator\examples\copy_add.json
```
