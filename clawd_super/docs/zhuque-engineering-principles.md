# 朱雀工程原则

## 1. 工程定位

`clawd_super` 是朱雀的工程目录。这里的文档、行为模型、RTL 和验证资产共同服务于朱雀本身的架构目标与实现目标。

## 2. 先文档，后实现

所有域统一按以下顺序推进：

1. 文档
2. 行为模型
3. RTL

如果一个域的接口、状态和事务没有在文档里定义清楚，就不直接进入 RTL。

## 3. 命名规则

- 顶层 codename 固定为 `zhuque`
- 中文名固定为 `朱雀`
- 文件名采用英文和下划线
- 模块名要表达职责和边界

## 4. 文档职责

文档要定义：

- 模块角色
- 输入输出
- 关键状态
- 正常事务
- flush、replay、recover、fault 等特殊事务
- 后续行为模型与 RTL 的落点

## 5. 行为模型职责

行为模型要表达可执行语义，而不是形式上的文件覆盖。每个域至少覆盖：

- 正常输入输出
- backpressure
- replay
- flush
- 恢复
- 关键统计或可观测输出

## 6. RTL 职责

RTL 要把行为模型拆成稳定的时序结构，并保证：

- 端口清楚
- reset 清楚
- 时序边界清楚
- 状态寄存清楚
- 可独立验证

## 7. 分层规则

每个域尽量拆成：

- package / contract
- data path
- control path
- orchestrator
- primitive

这样可以保持文档、行为模型和 RTL 三层的一致性。

## 8. 接口规则

接口优先强调语义、边界和可验证性：

- 数据载荷和控制载荷分开
- cancel/flush/replay/fault 显式化
- 资源阻塞显式化
- timing 假设写清楚

## 9. 全量推进原则

朱雀从文档阶段开始就按全量设计域组织。每个一级设计域都要有正式规格，不允许只有目录名、没有域定义。
